# Scenario and architecture planning

Contoso Forge keeps generation, planning, compilation and execution separate. The C# generator simulates the business source system and preserves its independent truth manifest. The C# planner describes the chosen deployment. Compilation writes adapters and definitions. Runtime execution remains an explicit subsequent action.

```text
business scenario + architecture preset + overrides
                         |
                        PLAN
                         |
                    ResolvedPlan
                         |
             DAG, capabilities, manual steps,
             credentials, costs and readiness
                         |
                       COMPILE
                         |
                 optional EXECUTE
```

## CLI

```powershell
dotnet run --project DatabaseGenerator -- forge scenarios list
dotnet run --project DatabaseGenerator -- forge presets list
dotnet run --project DatabaseGenerator -- forge plan --project examples/free-gcp-connect.project.json
dotnet run --project DatabaseGenerator -- forge plan --project examples/free-gcp-connect.project.json --output out/connect-plan.json
dotnet run --project DatabaseGenerator -- forge plan --project examples/local-fast-plan.project.json --output out/local-plan.json
dotnet run --project DatabaseGenerator -- forge plan --project examples/free-gcp-connect-ml.project.json --output out/ml-plan.json
dotnet run --project DatabaseGenerator -- forge compile --project examples/free-gcp-connect.project.json --output out/connect-compiled
```

Plan accepts an optional `--pipeline` to inspect a custom neutral graph, `--preset` to override deployment selection, and `--scenario` to apply an explicit business profile. Without `--output`, it prints a readable summary; with `--output`, it writes the versioned deterministic JSON contract. Invalid combinations fail with a nonzero exit code before writing a plan. Plan never loads credentials, starts processes or contacts a runtime. The CLI reads only supplied local inputs and writes the requested plan file.

The new `forge compile` command includes `plan/resolved_plan.json` in its manifest. Existing `forge pipeline compile` and ordinary `forge generate` retain their historical output set. This makes planning opt-in and preserves all default generated bytes. Compilation alone does not generate missing business data; use the existing `forge generate` flow for a runnable source package.

## Scenarios and profiles

| Business scenario | Intent | Explicit selection profile |
| --- | --- | --- |
| `retail.customer_satisfaction` | Orders, shipment experience, returns, support, reviews and injected data quality/CDC/SCD2 cases | Historical default generation |
| `retail.customer_satisfaction_ml` | The same entity graph with chronological classification intent | 1,200 orders, 240 customers, 48 products, 365 days; 14-day label embargo |

The optional envelope field `businessScenario` selects the business intent. `sourceProject.scenario` remains the existing V1 entity graph. Applying a different scenario explicitly selects its quantity/horizon profile and preserves deployment, project name, seed, start date and store count. Re-selecting the current scenario preserves custom quantities. Reading, planning or compiling an existing document never silently applies a profile.

Explicit `generation.timeSpanDays` requires at least as many orders as days. Dates cycle across all requested days, so every day receives at least one order. A shorter order count is rejected with a useful diagnostic. Omission preserves the historical 60-day cycle and serialized fingerprints exactly, including configurations with fewer than 60 orders. The existing 1,200-order / 365-day ML fixture is unchanged. A sufficiently long horizon does not itself prove viable ML classes; the measured label/partition guard remains mandatory before training.

## Presets and capabilities

`free-gcp-lab` remains classic Colab. `free-gcp-connect` explicitly selects local Spark Connect 4.0.4 inside Colab, local Parquet Silver, native BigQuery Sandbox batch loading, Airflow 3 on Minikube with GitSync, and OpenTofu intent. The manual external Colab handoff remains visible. dbt Gold and optional BQML are separate generated adapters, with their standalone execution boundaries stated in the plan.

Local Spark, local fast, Fabric, Databricks and Iceberg selections remain available. A valid architecture describes intent; its stages state whether the neutral compiler actually maps that operation. Existing Docker/Spark, DuckDB, Fabric and Databricks reference exporters remain intact. Pandas, Polars, MotherDuck, Iceberg/BigLake and future NoSQL integrations gain no runtime dependencies in this pass.

The shared resolver requires Git only for `dagSource=github-gitsync`. Local DAG/source plans accept absent or empty Git configuration. Supplied nonempty repositories still undergo HTTPS, credential and traversal checks. Placeholder repository/project IDs can be planned but must be replaced before execution; the planner does not inspect account permissions or remote paths.

## Readiness and evidence

Validation uses `declared -> generated -> parses -> executes -> tested -> reconciled`. Implementation status is independently reported as `executed`, `runnable`, `generated`, `reference-only` or `unsupported`. Every evidence entry explains its scope and points to a versioned observation. Historical adapter success never means the current project ran: each new plan explicitly reports `currentExecutionStatus=not-executed`.

`overallImplementationStatus` uses the most conservative stage status: `unsupported > reference-only > generated > runnable`. Historically `executed` adapters contribute runnable capability; they never promote a new plan to executed. Generated deployment stages keep `free-gcp-connect` at `generated`, while `local-fast` and `open-lakehouse-iceberg` remain `reference-only`.

Hosted classic and Connect-local Spark have separate evidence. The successful native BigQuery/dbt runs used classic mode. Minikube's prior successful result adoption used a local Git server. These observations do not prove the full composed Connect-to-BigQuery-to-public-GitHub architecture. IaC parsing is not infrastructure apply. Native ML feature SQL and offline label viability are not model training.

No final Power BI TMDL deployment is added. The JSON bridge preserves project/resolution/run/truth manifests and source, Gold, semantic intent and KPI models, alongside the optional resolved plan. The repository's existing semantic-intent starter is named `models/semantic_model.json`; the pack's conceptual `models/semantic_intent.json` name is mapped to that actual artifact. Planning neither renames the legacy file nor advertises a nonexistent replacement.

## Pipeline Studio

The WPF editor provides scenario and architecture selection, Plan, the resolved graph and architecture summary before compilation. It calls the same C# resolver as the CLI. Stage nodes expose engine/runtime, readiness and manual checkpoints; the summary explains formats, storage, warehouse, credentials, costs and evidence scope. The editable activity graph remains available. Edits invalidate the plan and compiled previews; existing pending-edit and companion-file protections remain in place.

See [the Windows editor instructions](../ContosoForge.PipelineStudio/README.md) and the local pass evidence under `artifacts/v131-plan/`.
