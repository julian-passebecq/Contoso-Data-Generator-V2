## Project and Studio integration

The existing optional product contract accepts `version: "1.6"` as well as `1.5`; the outer project stays `1.2.0`. Three examples share byte-identical deterministic causal-v1 sources:

- `examples/v16-local-duckdb.project.json`: `local-fast`.
- `examples/v16-local-polars.project.json`: `local-polars`.
- `examples/v16-local-pandas.project.json`: `local-pandas`.

Each uses local-process, local Parquet, tableFormat=none and warehouse=duckdb. Studio discovers the presets from the same registry, displays the selected engine and warehouse, preserves the version when applying product settings, and plans/compiles/runs the same factory graph. Per-activity engine overrides that differ from the compiled architecture fail instead of silently executing another engine. Other engine/runtime/storage/format combinations retain explicit unsupported/reference boundaries. No product opt-in retains the legacy reference behavior.

Run storage intentionally remains `.forge/v15/<run-id>/`: V1.6 extends the established factory artifact and stage contracts, including existing consumers and tamper checks. `silver_contract.json` and observed engine/version metadata are additive. The transformation engine and dbt warehouse are separate concepts; adding a preset does not create a second planner.

## Adapter behavior

Both adapters implement the existing whole-row deduplication, earliest-ingestion CDC/event selection, SCD2 lead windows and delete closures, ingestion lag and strict >24-hour late flags, valid shipments/reviews and quality quarantine. They use the complete source contract and validate CSV headers. Decimal/timestamp fields have explicit parse rules; there is no schema inference. Both persist real Bronze and Silver Parquet.

Polars **1.44.1** was rechecked as stable on [PyPI](https://pypi.org/project/polars/). pandas stays **2.3.3**, with DuckDB **1.4.5**, dbt-core **1.11.14**, dbt-duckdb **1.10.1**, sklearn **1.7.2** and Arrow **23.0.1**. No unrelated upgrades or release candidates were introduced. Polars uses LazyFrame expressions and `collect(engine="streaming")`; explain plans are retained and evidence explicitly declines to claim universal streaming. pandas performs the transformations itself; tests disable DuckDB connections while both DataFrame adapters run. Arrow only supplies typed pandas Parquet I/O and neutral comparison reads.

## Reproduction

Install the pinned runtime and validators in an isolated environment, then use a fresh output directory:

```powershell
dotnet test ContosoDGV2.sln --configuration Release
.tools/v15/Scripts/python.exe -m pip install -r DatabaseGenerator/Forge/Templates/v15/requirements.txt jsonschema==4.23.0 nbformat==5.10.4
.tools/v15/Scripts/python.exe scripts/run_v16.py --output out/v16-release --build-evidence
.tools/v15/Scripts/python.exe scripts/test_v16.py --gate out/v16-release --diagnostics artifacts/v16/negative-parity -v
```

On Linux replace the Python path with the active venv interpreter. Strict Evidence builds require Node/npm (CI pins Node 22). The gate invokes C# generation and the existing neutral runner separately for each engine, validates generated packages, executes dbt/ML/Evidence and V1.5 regressions, then writes actual `engine_parity.json`. It records checkout revision and dirty state; release evidence should come from a clean committed checkout. Logs are kept per engine. A failed stage or mismatch gives a nonzero exit.

The [canonical encoding specification](v1.6-canonical-encoding.md) defines every logical schema/value/hash rule, diagnostic bound and memory limitation. `engine_parity.json` includes all 13 governed tables, source and run identities, exact runtime versions, physical artifact integrity, logical schema/count/key/null/hash results, and bounded mismatch diagnostics. Matching KPIs alone never certify parity.

## Separate actual Spark parity

`spark-parity-v16` runs preserved Spark **4.0.4** Bronze/Silver business transforms, adapting only Bronze I/O to Parquet. This is an isolated real classic Spark run, compared with the same neutral comparator. The existing classic/Connect workflows remain intact. Spark parity is not inferred from historical runs and does not imply a new local Spark factory preset or hosted Colab execution.

```bash
python scripts/run_v16_spark.py --root out/v16-release/duckdb --state out/v16-release/spark-state
python out/v16-release/duckdb/factory/parity.py \
  --run duckdb out/v16-release/duckdb out/v16-release/duckdb/.forge/v15/v16 \
  --run polars out/v16-release/polars out/v16-release/polars/.forge/v15/v16 \
  --run pandas out/v16-release/pandas out/v16-release/pandas/.forge/v15/v16 \
  --run spark out/v16-release/duckdb out/v16-release/spark-state \
  --revision "$(git rev-parse HEAD)" --output out/v16-release/spark_engine_parity.json
```

Use Linux/WSL, Java 17 and `pyspark==4.0.4`. Capture production builds and parity with `scripts/capture_v16_evidence.py --gate out/v16-release --spark-parity out/v16-release/spark_engine_parity.json --output docs/v1.6-evidence.json`; add `--ci-runs` with the exact six completed green workflow records after CI finishes.

## Gates and retained boundaries

`factory-v16` blocks on three complete local pipelines, strict report builds, canonical parity and negative tests. `spark-parity-v16` separately blocks on an actual Spark comparison. Existing `validate`, `free-gcp-contracts`, `factory-v15` and `pipeline-studio-windows` remain required release gates; the Windows workflow additionally renders both new engine presets. Legacy 152-artifact compatibility, causal controls, point-in-time/embargo/validation-only selection, dbt reconciliation, cloud contracts and Spark classic/Connect remain covered.

Measured results and all six completed implementation Actions runs are recorded in [v1.6-evidence.json](v1.6-evidence.json): 246 .NET tests, 123 distinct Python checks (three optional integrations skipped), four WPF smokes, three full local pipelines and actual four-engine Silver parity. Final branch checks are separately attached to the PR. Do not interpret an offline plan's historical adapter evidence as execution of that project. Cosmos/Airflow task execution, native MotherDuck/Dive, hosted notebooks and native cloud work are not recertified by local parity. Iceberg, NoSQL, FastAPI, Polars Cloud and V1.7 features remain outside this release.

Two architectural constraints should guide later work: CDC ties need a governed conflict policy before external ingestion expands, and the current canonical comparator needs bounded external sorting for larger datasets. Preserve one source contract and planner when addressing either. Cosmos also still needs invocation-bound task evidence before its duplicate dbt build can be removed safely.
