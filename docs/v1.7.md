# V1.7 Modular Journeys & External Labs

V1.7 extends the existing C# project contract, planner, compiler, runtime adapters and WPF Studio. It starts from PR #3's merged main, `ea7c47a6db64de0e91b69b2259c7d48f744e15cc`. It supersedes the proposed FastAPI release. Historical V1.5/V1.6 templates and evidence retain their original scope.

## Choose a goal and a boundary

| Goal | Configuration | Stop stages |
| --- | --- | --- |
| `data-only` | Empty `selectedKpis`, `analysis.kind=none` | generate, bronze, silver, gold |
| `kpi-semantic` | At least one governed KPI, `analysis.kind=none` | Any boundary; semantic/report stages publish only selected KPIs |
| `specific-ml` | Explicit sklearn or Spark ML algorithm | Any boundary; training begins at analysis |
| `automl` | `analysis.kind=mljar`, runtime Kaggle, bounded CPU budget | Any boundary; the analysis stage exports or executes the notebook |

All V1.7 projects require `goal`, `stopAfter`, `selectedKpis`, `analysis` and `publishTargets`. `stopAfter=publish` requires a Hugging Face or Dive target. A warehouse is required for Gold and later. The generated ML scenario currently supports binary dissatisfaction classification; unsupported labels/problem types fail explicitly. MLJAR itself supports regression, but Forge has no governed generated regression label in this release.

```json
{
  "version": "1.7",
  "goal": "kpi-semantic",
  "stopAfter": "report",
  "selectedKpis": ["gross_sales_amount", "return_rate"],
  "analysis": {"kind": "none"},
  "publishTargets": []
}
```

Use this object as `product` in an existing Studio project. The examples are complete projects. Logical stages compile to the existing factory activities: generate/verify, Bronze, Silver plus validation/optional recipe, Gold plus reconciliation, semantic, analysis, report, publish. The compiler excludes downstream activities; the runner rejects direct attempts to execute them. Generate produces source/truth/contracts; its verify operation performs no Bronze work. Generated downstream templates are design assets, not execution evidence.

```powershell
dotnet build DatabaseGenerator --configuration Release
python -m pip install -r DatabaseGenerator/Forge/Templates/v15/requirements.txt
dotnet run --project DatabaseGenerator --configuration Release --no-build -- forge generate --project examples/v17-kpi-duckdb.project.json --output out/my-v17
python out/my-v17/pipeline/run_local.py --root out/my-v17 --run-id experiment-1
python out/my-v17/factory/build_evidence.py --state out/my-v17/.forge/v15/experiment-1
```

Use a fresh run ID/output directory when changing intent. The `.forge/v15/<run-id>` storage namespace remains for compatibility; `run_evidence.json.contractVersion=1.7` identifies the new contract. Report creates an Evidence package; the separate strict production-build command requires Node/npm. No report package or build runs before the report boundary.

## Engines, Gold and semantic scope

DuckDB, Polars, pandas and Spark persist independent typed Bronze Parquet. Silver reads those persisted files and verifies Bronze identity, counts and hashes before/after transformation. The existing deduplication, CDC ordering, SCD2, late-arrival, valid shipment/review and quarantine semantics are reused. Polars and pandas perform their own transformations. DuckDB remains the independent validator and shared local dbt warehouse. Spark requires pinned PySpark 4.0.4 and Java 17.

`factory/kpi_goals.json` describes the five starter KPIs: order count, gross sales, return rate, on-time delivery rate and average review rating. The compiler traverses actual governed dbt `ref`/`source` dependencies. `models/lineage.json`, `semantic_model.json`, `kpi_catalog.json` and `query_examples.sql` describe the selected publication and dependency closure. Semantic measures select canonical Gold columns; UI/report adapters contain no alternative KPI formulas. Shared source fixtures and the 27-model dbt project still materialize in full. **Physical pruning is not implemented.**

Examples include DuckDB/Polars/pandas KPI reports, Bronze-only data, a recipe, specific sklearn, Spark ML/Colab, Kaggle AutoML, MotherDuck and Cosmos. Studio opens a goal-first KPI example, offers the eight journey steps, and retains engine/runtime overrides under Advanced. Old projects retain the original editor flow and serialization.

## Specific ML and bounded AutoML

Specific sklearn filters the candidate set to the chosen algorithm. Spark ML retains its comparison with the dummy baseline and explicit logistic regression, random forest or gradient boosting selection. Colab notebooks and Databricks sklearn exports remain available. Spark ML supports local Spark/Colab; Databricks-hosted execution is not certified. Spark ML is never labelled AutoML.

MLJAR Supervised **1.3.2** uses Explain by default, with explicit advanced Perform/Compete modes and a CPU-only candidate set: Baseline, Linear and Decision Tree. The default budget is 300 seconds (accepted range 30–3600); the notebook wrapper enforces a subprocess deadline of budget + 60 seconds. External polling has its own bounded deadline, at most 7200 seconds. At least one non-baseline candidate must train successfully. The baseline may legitimately win on validation.

The governed feature allowlist and post-outcome exclusions remain authoritative. Numeric Parquet decimals are explicitly typed before training. Custom chronological train/validation indices enforce the 14-day embargo; final test rows never reach `fit`. Validation logloss selects the model, validation F1 selects the threshold, and selection metadata is frozen before final test scoring. Outputs include leaderboard, validation/test metrics, predictions, selected-model metadata, available importance and native reports. The report labels the measured framework explicitly.

## Kaggle execution

Install `factory/external-requirements.txt` and supply official Kaggle CLI authentication externally. No tokens belong in project JSON. Set `analysis.execute=true`, explicit `datasetId` and `kernelId` (`owner/slug`). Set `versionDataset=true` only to version an existing private dataset. `requireExecution=true` turns unavailable execution into failure. Default examples select export only.

The adapter uses pinned official Kaggle CLI **2.2.4** to create/version a private dataset, wait for a ready dataset version, push a private CPU notebook, poll kernel status with bounded backoff, and retrieve completed output. The notebook verifies the exact mounted package and package-manifest hash before running. The result contract binds run ID, source fingerprint, project hash, Gold feature hash, package hash, dataset/kernel/version, target and temporal partitions. Import checks every file hash, held-out order key and label, then independently recomputes classification metrics from returned predictions. Timeout/failure cannot produce successful imported evidence. Returned serialized model objects are not deserialized by the importer.

`kaggle_execution.json` records actual submission/status observations and remote identity only when they exist. Without authentication, the dataset/notebook package remains `exported-not-executed`. A real local execution of the notebook worker proves the bounded MLJAR implementation; it **does not prove execution in a Kaggle account**.

CLI behavior is based on the official [dataset commands](https://github.com/Kaggle/kaggle-cli/blob/main/docs/datasets.md), [kernel commands](https://github.com/Kaggle/kaggle-cli/blob/main/docs/kernels.md) and the pinned distribution. Dataset status supports JSON; kernel status is parsed from the CLI's textual status. Temporal validation uses MLJAR's documented [custom CV API](https://supervised.mljar.com/api/).

## MotherDuck, dbt and Dive

Set the architecture warehouse to `motherduck` and provide a typed MotherDuck publish target with a safe, fresh database name. DuckDB, Polars and pandas validated Silver can feed it. With `execute=true` and `MOTHERDUCK_TOKEN`, the adapter creates a new database (existing names fail), publishes Silver, checks all 13 counts and executes one dbt build against `md:<database>`. KPI reconciliation and semantic queries use the remote warehouse. Local DuckDB is never substituted for remote execution.

`motherduck_build.json` and `motherduck_reconciliation.json` are immutable stage receipts. `motherduck_execution.json` is the checked aggregate summary, including final reconciliation and optional Dive result. `createDive=true` plus the publish boundary creates a Dive only from reconciled native Gold. Its scoped SQL reads the selected canonical Gold columns. Authentication is external; logs are sanitized on failure.

Without credentials, the receipt is `exported-not-executed` and dependent remote stages retain that state. No fake remote KPI values or Dive URLs are emitted. Account limits and [MotherDuck pricing](https://motherduck.com/pricing/) apply. V1.7 MotherDuck + Cosmos is an explicit unsupported combination; direct dbt is supported.

## Hugging Face results and static Space

Add a `huggingface` target and stop at publish. Export requires actual, hash-bound ML metrics from the current run. The model card describes synthetic data, prediction/label times, leakage exclusions, feature availability, partitions/embargo, selection/threshold provenance, final test metrics and limitations. The package includes metadata, metrics, leaderboard, sample predictions and available importance. Portable model weights are not produced by these adapters; executable pickle/joblib files are excluded and `modelWeightsIncluded=false` is explicit.

The Space is self-contained HTML plus JSON with `sdk: static`; no paid model serving or live inference is needed. Publication uses pinned `huggingface_hub` **1.30.0**, external write authentication (`HF_TOKEN` or the official cache), `execute=true`, and explicit `modelRepoId`/optional `spaceRepoId`. Targets are private by default. Existing visibility must match intent before upload. Receipts retain actual returned commit revisions and package hashes. Missing authentication yields `exported-not-published`. Missing measured ML results yields no invented model card.

The implementation follows Hugging Face's [upload guide](https://huggingface.co/docs/huggingface_hub/guides/upload) and [static Space configuration](https://huggingface.co/docs/hub/spaces-sdks-static).

## Neutral wrangling recipes

`product.recipe` follows `schemas/wrangling-recipe.schema.json`: source, select, rename, cast, derive, filter, join, lookup, conditional split, aggregate, deduplicate, window and sink. Expressions are typed trees, for example `{"operator":">","args":[{"field":"OrderKey"},{"value":10}]}`. Identifiers, fields, types, operators, dependencies and materialization row budgets are checked. No user SQL, Python, shell or filesystem paths are accepted.

Recipes read governed Silver and produce separate `wrangling/*.parquet` derived assets with compiled SQL/Polars plans and receipts. They do not overwrite canonical Silver, Gold or truth. DuckDB and Polars are the supported recipe engines; pandas/Spark recipe mappings reject explicitly. Conditional-split branches use separate matched/unmatched steps; lookup requires unique right keys. Inner/left joins require explicit renaming of overlapping non-key columns. Windows support deterministic row number and cumulative sum. `maxRows` defaults to 100,000 and is bounded to one million. This is a row-materialization guard, not a provider memory quota. Paid Azure Data Factory execution remains outside this release.

## Compatibility, verification and boundaries

The old BigQuery/BQML, Colab, Databricks exports, Spark classic/Connect, Airflow/Cosmos, Evidence and OpenTofu/Terraform paths remain. Their historical ledgers are unchanged. V1.7 does not promote generated plans to executed/reconciled based on those historical records. V1.7 Cosmos uses the existing single-build Watcher/adoption contract and a fresh real DagRun gate; short Cosmos journeys require plain dbt or the neutral runner instead.

Use `--spark` with the pinned Spark runtime. Release capture requires a clean measured checkout; it rechecks identities, persisted hashes, 13-table logical parity, stage boundaries, strict report builds and local MLJAR results. CI uploads receipts, dbt artifacts, local MLJAR reports, external packages and test logs. The current handoff records exact workflow IDs and separates implemented adapters, real local proof and unexecuted external accounts.

V1.8 candidates: physical dependency pruning; governed regression targets; safe portable model serialization; verified account-backed Kaggle/HF/MotherDuck runs; broader recipe type/null semantics and Spark compilation; persistent orchestration/retry certification. These are explicit boundaries, not evidence of current execution.
