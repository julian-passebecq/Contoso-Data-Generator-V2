runs. First, it issued a **Spark-only work order** executed in WSL Ubuntu. Then it

Generated artifact publication to GitHub remains a separate unexecuted gate.
The default full `spark-and-bigquery` execution scope remains unchanged.

## Fixes discovered by executing the lab

The initial Helm install waited on Airflow pods that themselves waited on database
migration. The chart's default migration Job is a post-install hook, so `--wait`
prevented that Job from starting. The generated values now set
`migrateDatabaseJob.useHelmHooks: false`. The initial lab was recovered by running
the equivalent official migration Job; Helm revision 2 then installed the corrected
values and successfully ran its ordinary migration Job. A separate empty-cluster
install after this fix was not repeated.

The chart also creates the LocalExecutor scheduler as a StatefulSet with its
default persistence settings. Instructions now select the scheduler pod by label,
instead of assuming it is a Deployment. Bootstrap and smoke commands use an
explicit context and preserve the user's current kubectl context.

The initial full work order correctly failed because the sample still had
`your-gcp-project`; [that failure](../artifacts/v1.3-minikube-first-run.json) is
retained. An explicit `executionScope: "spark"` DAG run then exercised the local
cycle without fabricating a Google project ID or claiming warehouse success.
The default is still `spark-and-bigquery`, and scopes are checked against the
issued work order.

Docker Desktop initially failed on a stale telemetry socket. Only its socket
directory was renamed and retained as a backup; Docker data and existing lab
volumes were preserved. The environment evidence records the exact backup path.

## Reuse the runner

After publishing a complete generated sample to the configured GitHub path,
install and trigger a new full run from the repository root:

```sh
python scripts/run_minikube_smoke.py --project <generated-project> --context contoso-forge --install --trigger --run-id <new-run-id> --output artifacts/minikube-runtime.json
```

For a separately labeled Spark-only run before Google authentication, add
`--scope spark`. Equivalently, Airflow's trigger configuration is
`{"executionScope":"spark"}`; the local sequential runner accepts `--scope spark`.
Invalid scopes fail before issuing a package. The work-order scope cannot change
when resuming a run.

The generated Minikube README explains copying the work package out and publishing
the actual returned result atomically. Observe the same run after returning it:

```sh
python scripts/run_minikube_smoke.py --project <generated-project> --context contoso-forge --observe-run --run-id <same-run-id> --scope spark --output artifacts/minikube-runtime.json
```

Use the original scope when observing. The runner records separate gates and
never promotes a local Git/Spark result to full GitHub/Colab/BigQuery validation.
The current isolated cluster, local Git container, and state volumes remain
available. To pause only this lab, use `minikube stop --profile contoso-forge-v13`
and `docker stop contoso-forge-v13-git`.
