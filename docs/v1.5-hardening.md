## Deterministic causal controls

Legacy generation remains the default, including the audited 152 artifact hashes. To opt in, add this to `sourceProject.generation` (or `generation` in a source ProjectSpec):

```json
"ml": {
  "profile": "causal-v1",
  "positiveOutcomeRate": 0.10,
  "signalStrength": 0.5,
  "noiseLevel": 0.1
}
```

The profile is required; the three numeric fields have the shown defaults and must be finite in `[0,1]`. See [the causal example](../examples/v15-local-ml-causal.project.json). Positive means **dissatisfaction**, not satisfaction. Legacy injector frequency remains fixed.

At delivery, let `r=positiveOutcomeRate`, `s=signalStrength`, `n=noiseLevel`, and `d=(deliveredAt-promisedAt)/2 days`. This scenario's delivery delays are uniformly drawn from -2 through +2 days, so `d` is centered and bounded by ±1. The adverse outcome probability is `r + s*(1-n)*min(r,1-r)*d`. A separate SplitMix64 stream, seeded by `generation.seed XOR 0x43A91D27`, samples the outcome. Signal zero or noise one removes the delivery-delay association; noise mixes the causal probability toward an independent Bernoulli rate `r`. Bernoulli sampling remains even at noise zero: this is a stochastic causal scenario, not a guarantee of perfect separability. The rate is an expectation, not a forced class quota, and sampling/quality quarantine can change the realized Gold prevalence.

The profile emits one review per order two days after delivery and aligns existing closed support-survey scores to the sampled outcome. The existing invalid-review injector still quarantines one review. Orders, dimensions, shipments, shipment events, returns and CDC bytes do not depend on any outcome control. Neither the latent outcome nor its probability is exported as a feature. The dbt Gold label, prediction-time feature allowlist, label maturity and 14-day embargo remain authoritative. No output label is back-propagated into a prediction-time feature.

## Validation threshold analysis

Every model retains validation/test metrics at **0.5**. Each model also gets an operating threshold maximizing **validation F1**, over distinct validation scores plus 0, 0.5 and 1. The decision rule is `probability >= threshold`. Ties prefer closest to 0.5, then the higher threshold. The selected model remains the maximum validation Average Precision candidate, with the existing deterministic name tie-break. All thresholds and the selected model are frozen before any test predictions are evaluated. Test metrics are descriptive and never choose the model or threshold; the shared validation set means its optimized F1 is not an unbiased performance estimate.

`metrics.json` contains `baselineThreshold` and per-model `thresholdAnalysis` with selection provenance, validation tradeoffs, selected threshold and validation/test metrics and confusion matrices. Persisted predictions include both decisions. The model card explains selection. The ledger retains operating-point metrics and hashes the complete curve artifacts. The sklearn and secondary Spark ML paths use the same evaluator.

Evidence projects these measured records into model comparison, validation PR curves, threshold/F1 curves, threshold tables, and both confusion matrices. All threshold selection and metric calculations stay in Python ML; all KPI and label logic stays in dbt. ML-disabled BI remains supported.

## Cosmos remains generated/unverified

The optional Cosmos DAG currently performs dbt **twice**: its `DbtTaskGroup` runs model/test tasks against `cosmos.duckdb`; `finish_run` then performs a full plain build against `warehouse.duckdb` to produce complete authoritative `manifest.json`/`run_results.json` for reconciliation. The second result proves only the plain invocation. Cosmos's last per-node `run_results.json` cannot prove the entire TaskGroup.

The planner explicitly retains generated status for the Cosmos dbt stage, with no borrowed plain-dbt execution evidence. Do not promote it to runnable until actual Airflow/Cosmos tasks execute and complete per-node results are collected with unambiguous invocation, database, input, model/test coverage and hash bindings. Parsing the DAG or manifest is insufficient. Removing the duplicate dbt execution needs that evidence design first and is outside this hardening pass.
