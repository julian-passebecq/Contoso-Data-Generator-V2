## Product and execution

Studio exposes **Business → Data → Pipeline mode → Architecture → Orchestration → dbt → ML design → BI & Validation → Run → Monitor / Results**. It starts at Business. The existing graph, activity inspector, parameters, architecture overrides, connection references, destination editor, compiler and previews remain available. A pending edit invalidates the plan and disables local execution. Untouched default graphs follow product settings; authored custom graphs are preserved and unsupported bindings fail explicitly.

`examples/v15-local-bi.project.json` is the 60-order business/BI fixture. `examples/v15-local-ml.project.json` is the 1,200-order, 365-day ML fixture. In Studio, Plan the selected revision, set the Python executable to the installed environment, and choose Run local. It creates fresh source/output/run directories, executes the generated neutral runner, and displays measured evidence. Build Evidence performs a separate real npm production build. Open Evidence report serves the built directory on loopback HTTP; closing Studio stops that preview server. UI smoke tests cover authoring and rendering; actual pipeline execution was tested through the same generated neutral runner, separately from the folder picker.

The executable local graph is:

```text
deterministic C# sources + independent truth manifest
  → verify source/compiled hashes
  → typed DuckDB Bronze and Silver
  → persisted Bronze/Silver row-count reconciliation
  → dbt staging → intermediate → marts/Gold → dbt tests
  → independent canonical Gold KPI reconciliation
  → optional sklearn training or explicit notebook export
  → Evidence BI & Validation package
  → optional strict Evidence production build
```

DuckDB executes the existing scenario semantics: duplicate removal, CDC event ordering, SCD2 history, late-event flags, tracking-number and review quarantine. It writes actual Parquet. dbt runs as a subprocess, retains `manifest.json`, `run_results.json` and logs, and rejects missing/skipped/failed model or test results. Gold business logic stays in dbt. The fact join is visibly extracted to `intermediate/int_customer_experience.sql`; downstream Gold and the new daily mart use it.

Each local run lives under `<generated-root>/.forge/v15/<run-id>/`. Its identity includes the source dataset fingerprint and source, truth, project and compiled-manifest hashes. Stages record timestamps, observed results, artifact hashes and runtime versions. A later stage verifies prior artifacts and prerequisites. Reusing a successful stage verifies it before returning; source edits require a fresh output/run. The neutral runner retains retry/timeout handling. A killed process may leave `.running`; verify that no writer is active before manually removing that single stale lock. Failed runs retain their logs and do not become successful training/report evidence.

## ML Lab

The selected customer-satisfaction problem derives one prediction per completed order at delivery. The label is an adverse valid review or closed support score within the next 14 days; absence becomes negative only after maturity, and is not proof of satisfaction. Features have an explicit availability map; shipment event time **and** ingestion time must precede delivery, and customer CDC availability must precede the order. Post-outcome ratings, review text, returns, refunds, support closure, late-arrival aggregates and identifiers are excluded from estimator inputs.

Preprocessing is fitted on training rows only. Splits follow prediction timestamps with timestamp ties kept together; earlier labels must mature strictly before the next partition. A 14-day embargo and minimum two examples of each class per partition are enforced. Parquet metadata is checked before sklearn materialization, then actual frame memory is checked. The standard budget is 256 MiB. Large marts fail with guidance to reduce the mart or use the Spark educational path; there is no unrestricted `toPandas()` default.

The real ML fixture retained 796 training rows (75 positive), 140 validation rows (10 positive), and 180 test rows (17 positive). Logistic regression was selected by **validation Average Precision only**. On held-out test data its AP was **0.187540**, ROC-AUC **0.765428**, and F1/precision/recall were **0** at the fixed 0.5 threshold (TN 163, FP 0, FN 17, TP 0). Execution succeeded; those threshold results are poor. Random forest and histogram gradient boosting are reported alongside the dummy baseline; the test set did not choose the winner.

Artifacts include `spec.json`, `features.json`, `run_config.json`, `leakage_report.json`, `metrics.json`, `predictions.parquet`, `split_assignments.parquet`, validation permutation importance and `model_card.md`. AP, ROC-AUC, F1, precision, recall, confusion matrices and PR curves are measured. A small candidate registry also includes dummy/linear/ridge/tree regression, KMeans and IsolationForest for relevant future scenarios; the generated V1.5 scenario and training entry point are binary classification. No giant AutoML or production model deployment is added.

## BI and external paths

Evidence consumes actual Gold tables, KPI catalog, semantic tables/relationships, truth manifest, run evidence, dbt lineage/results and measured ML outputs when present. The KPI table shows measured and expected values first. Daily sales charts consume the existing daily/store dbt mart. Report queries only project/order already-built data; they contain no independent KPI or label expressions. Semantic interchange expressions are retained as metadata, not evaluated as a second transformation layer. The report includes an explicitly labelled pre-BI pipeline snapshot; final execution lives in `run_evidence.json`, and render status in `bi/build_evidence.json`.

Evidence is the pinned open-source npm implementation (`@evidence-dev/evidence 40.1.8`, core components `5.4.2`, CSV `1.0.16`, TypeScript `5.4.2`), based on the [official OSS template](https://github.com/evidence-dev/template/tree/ec9e0f59c9b86bc47b7dcb8878b7981dd9e5e287). Both builds were measured with Node `21.7.1` / npm `10.5.0`; npm emitted engine/deprecation warnings but strict builds passed. New CI uses Node 22. Direct dependencies are pinned; npm lockfiles and Python runtime versions are captured per run, not a universal platform-independent lock.

## Reproduce locally

Use fresh output directories. From the repository root in PowerShell, with .NET 8, Python 3.13 and Node/npm available:

```powershell
dotnet test ContosoDGV2.sln
python -m venv .tools/v15
.tools/v15/Scripts/python.exe -m pip install -r DatabaseGenerator/Forge/Templates/v15/requirements.txt
dotnet run --project DatabaseGenerator --no-build -- forge generate --project examples/v15-local-bi.project.json --output out/v15-release-bi
dotnet run --project DatabaseGenerator --no-build -- forge generate --project examples/v15-local-ml.project.json --output out/v15-release-ml
.tools/v15/Scripts/python.exe out/v15-release-bi/pipeline/run_local.py --root out/v15-release-bi --run-id release
.tools/v15/Scripts/python.exe out/v15-release-ml/pipeline/run_local.py --root out/v15-release-ml --run-id release
.tools/v15/Scripts/python.exe out/v15-release-bi/factory/build_evidence.py --state out/v15-release-bi/.forge/v15/release
.tools/v15/Scripts/python.exe out/v15-release-ml/factory/build_evidence.py --state out/v15-release-ml/.forge/v15/release
.tools/v15/Scripts/python.exe scripts/test_v15.py --root out/v15-release-ml --state out/v15-release-ml/.forge/v15/release -v
.tools/v15/Scripts/python.exe -m http.server 8766 --bind 127.0.0.1 --directory out/v15-release-ml/.forge/v15/release/bi/evidence/build
```

Open `http://127.0.0.1:8766/` while the final command runs; stop it with Ctrl+C. The HTTP server is needed for the report's browser data/assets. On Linux use a venv's `bin/python` in place of `Scripts/python.exe`.

Pipeline modes currently select an exercise focus over reproducible full-batch CDC/SCD2/late-arrival/quarantine replay. They are not a persistent incremental service. Data volume/horizon/seed use the existing C# contract; injector frequency remains fixed. The opt-in causal-v1 ML profile now controls adverse-outcome rate, signal and noise without changing legacy defaults. The UI generation editor accepts this profile. Regression/clustering/anomaly scenario authoring, production model serving, embedded Dives, cloud deployment and additional transformation engines are outside the implemented slice. Source/dimension and temporal relationships assume this generated scenario's contracts, not arbitrary external source schemas.

Earlier failed development attempts are retained locally: an incompatible DuckDB CSV API argument, an ambiguous `gold` database/schema name, and an unpinned TypeScript peer dependency. They were fixed before the release runs above. No failed attempt was relabelled as successful. Dependency deprecation warnings are visible in logs; there were no failed release model/tests or Evidence builds.
