## Findings

### F001 — P1: preview does not validate receipt identity or hashes

Location: `ContosoForge.PipelineStudio/FactoryStudio.cs`, `OpenEvidenceAsync` (baseline around line 236); compare `DatabaseGenerator/Forge/Templates/v15/build_evidence.py` fields `runId`, `reportContractSha256`, `artifact`, `sha256`.

The preview gate checks an in-memory success boolean, receipt `status == built` and index existence. It does not compare the recorded run ID, contract hash or index hash before serving the file. An altered index or mismatched receipt can therefore be shown under the trusted result flow after a successful build.

Reproduced with a synthetic selected-run state using the real WPF window and `OpenEvidenceAsync(false)`: an index containing changed bytes and a receipt containing another run ID and deliberately incorrect hashes were accepted and served over loopback. The probe sets private selection fields by reflection, so it isolates the preview guard; it does not claim to reproduce a full generation/build workflow. The existing smoke tampers with report *source*, attempts a rebuild, and checks the reset boolean; it does not test tampering after a successful build with no intervening rebuild.

Required fix: S001 AC02/T02. Validate the persisted contract and selected identity on preview, without executing imported code. Do not overstate integrity beyond fields the receipt binds. Durable negative tests must include after-success tampering without first invoking a rebuild. Evidence: `artifacts/projectmanagement-bootstrap/preview-probe.txt` and `probe/Program.cs`.

### F002 — P2: applying another revision retains the old successful result selection

Location: `MainWindow.xaml.cs`, `Changed` (baseline around line 256), and `FactoryStudio.cs` result fields/reset/preview eligibility. Resets occur on project/pipeline load and starting a run; applying edits invalidates planning but leaves the previous successful result selection available.

The same probe applies a Bronze stop boundary after establishing a built report selection. The new project reports `stopAfter=bronze`, but the prior successful flag remains true and the prior report is still previewable. Keeping old results can be useful, but the current state model has no explicit relation between the editor's revision and selected historical run. History must not build on an implicit assumption that these are the same.

Required fix: S001 AC03/T03. Distinguish selected history from current revision, or clear selection when the revision changes. Preserve old files and measured outcomes; do not delete useful evidence. Add a durable test using an actual completed run plus an applied edit, and verify the visible identity/historical labeling, not only internal booleans.

### F003 — P1: preflight and runtime package requirements disagree

Location: `FactoryStudio.cs`, `ValidateRuntime` (baseline around line 81), versus `Templates/v17/run.py` around lines 84–85.

Studio chooses required imports according to the graph/engine. V1.7 execution nevertheless calls `metadata.version` unconditionally for DuckDB, pandas, Polars, PyArrow, dbt-core and scikit-learn after every successful dispatch, including verify. In an otherwise adequate DuckDB environment, absent metadata for an unused engine/ML library raises `PackageNotFoundError`, and the enclosing handler marks the stage/run failed. The fully populated local environment masks this condition. Review transitive imports as well as direct imports before defining the actual minimum.

Fault-injection reproduction uses the freshly generated `out/pm-bootstrap-report` DuckDB fixture, patches only Polars distribution metadata lookup to raise, and invokes the actual `run.execute(..., 'verify')`. See `artifacts/projectmanagement-bootstrap/metadata_probe.py` and its output. This establishes the failure path under simulated missing metadata; it is not evidence of a separately provisioned minimal installation.

Required fix: S001 AC04/T04. Align selected-path preflight with real requirements; unused optional version discovery must not fail the stage. Preserve mandatory dependencies and do not suppress arbitrary execution errors. Add a regression plus a clean/isolated dependency case when feasible.

## Sound decisions to preserve

`ApplyJourneySettings` now parses inputs and passes scenario/product changes through one draft in `StudioSession.ApplyProduct` before committing project/graph. This addresses the originally reproduced partial mutation; the fresh journey smoke passes. Keep semantic rejection and authored-graph coverage.

The report's immutable upstream snapshot avoids embedding an in-progress BI row as final status and avoids circular hashing. The separate build receipt is the right lifecycle boundary. Fresh focused report tests pass, including the ML-only empty-KPI regression and stored-threshold display. Extending preview validation should preserve this distinction.

Process execution drains stdout/stderr concurrently, uses an argument list and keeps a full log while bounding the UI display. These are useful foundations. New state/history services should preserve them rather than replacing the runtime architecture.
